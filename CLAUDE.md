# PBE Address Book ("Book")

Members-only directory web app for the ~700 living brothers of Phi Beta Epsilon (MIT), sibling to the Ghost newsletter site pbe400.org. The membership spans ages 18 up and is mostly well-connected, but it also includes older brothers, less confident users, and genuinely slow links — design for those **edges**, not as though they were the norm: be byte-frugal, calm, and legible.

## Development workflow

Sessions follow the committed **`dev-workflow` skill** (`.claude/skills/dev-workflow/`) — invoke `/dev-workflow` before starting any task that changes code or docs. The short version: discuss and plan first, wait for explicit approval; all work on a feature branch → PR; `/code-review` for deep changes, CI-green suffices for shallow follow-ups; merge per the skill's **tiered Gate 4** — in interactive sessions any change, deep changes and dependency upgrades included, may merge on green CI + clean review (**active for this repo**: CI enforces the full gate and branch protection requires it, D141/OFC-297; widened to deep changes by D188), while changes a `git revert` can't fully undo — infrastructure/secrets/IAM shared with production, the Ghost auth bridge, and data shape and migrations **while staging data survives deploys** (D189) — and every autonomous-session PR still wait for **Forrest's explicit OK**. Merging to main auto-deploys staging, so a merge is a deploy.

**Parallel sessions:** if another session may be concurrently active in this repo — and in any autonomous session, always assume one is — do **not** edit the main checkout. Create a git worktree under `.claude/worktrees/` and do all work there. The skill's "Parallel sessions and worktrees" section carries the landmines (absolute paths hit the wrong checkout; run `npm install` inside the worktree; remove it at close-out).

## Stack

npm-workspaces monorepo, TypeScript end-to-end with one shared `Profile` type (D3):

- `apps/web` — React + Vite + Tailwind v4 + shadcn/ui; TanStack Table/Virtual; React Router + nuqs.
- `apps/api` — Fastify on Cloud Run, bundled by esbuild; Firestore + private GCS image bucket. Firebase Hosting serves the SPA and rewrites `/api/*` and `/img/*` to Cloud Run (single origin).
- `packages/shared` — the shared `Profile` type, validation, capabilities, canonical names.
- `packages/help-content`, `tools/fake-data`, `tools/geo-data` (generates the committed proximity tables — D177), `tools/migration`, `infra/`, `e2e/`.

Tooling: Biome (format + lint), Vitest (unit + Firestore-emulator integration — emulator tests are `*.emulator.test.ts` and need JDK 21), Playwright + @axe-core/playwright, tsx for scripts.

## Commands

- `npm run verify:fast` — the **fast local lane** (gate-list sync, Biome, token drift, chip-palette drift, help-manual drift, proximity-table manifest drift, typecheck, unit/integration tests). Run this as you iterate: it catches the great majority of mistakes in seconds, without the slow tail.
- `npm run verify:gate` — the full local gate (gate-list sync, Biome, token drift, chip-palette drift, help-manual drift, proximity-table manifest drift, typecheck, build, CSP hashes, no-dev-provider, no-session-replay, bundle-size ceiling, unit/integration tests, emulator tests, e2e). **The authoritative run of this gate is CI's, on the pull request** (D143) — run it locally when the change touches what the fast lane doesn't cover (build output, CSP hashes, bundle size, emulator, e2e) or to debug a CI failure with a tighter loop, not reflexively before every push. CI runs the same steps individually — deliberately, for per-step timing and failure attribution (`ci-timing.mjs`) — and **`assert:gate-in-sync`, the first gate step of both pipelines, fails either side if the two lists ever drift** (D141/OFC-297). A new gate step still goes into both `package.json` and `ci.yml`; the guard makes forgetting one a red build instead of a silent hole.
- `npm run seed` — seed the emulator with fake data. Staging seed/link scripts live in `tools/fake-data`; provisioning playbooks in `infra/`.
- `npm run restore --workspace apps/api` — the **offline restore** (D101/D150): replaces `profiles`, `users` and `config` from a backup snapshot. Destructive by design and guarded accordingly (`--dry-run`, `--confirm <project-id>`, a maintenance pre-flight, a safety snapshot before the first delete). Read the procedure in `infra/DR-RUNBOOK.md` before running it; ⚠ a restore is invisible until the instance cold-starts. `--database <id>` and `--no-forensic-entry` exist only for the backup-integrity job's throwaway database (D151/D192); the second is refused on a default database.
- `npm run backup:verify --workspace apps/api` — the **backup-integrity check** (D102/D151, N190): reads a restored *named* database back against the snapshot it came from (freshness, exact content, real cache hydration, image manifest) and prints a counts-only verdict; exit 0/1/2. Read-only. Driven by the integrity job, never against a live database.
- `infra/verify-backup.sh` — the **backup-integrity job** (D151/D193): restores the source environment's newest backup into a throwaway named database in the separate `pbe-book-verify` project, runs `backup:verify`, and deletes the database from an EXIT trap. Scheduled weekly-then-monthly on Cloud Build (provisioned by `infra/provision-verify-project.sh`, Forrest's to run: it grants read on production's buckets); `ENV_FILE` names the SOURCE environment and has no default; `--dry-run`. In Cloud Build it keeps the restore's output (which can name brothers) out of the log. Procedure, first run and failure triage: `infra/DR-RUNBOOK.md`.
- `npm run genesis:convert --workspace apps/api` / `genesis:headshots` — the **genesis load** (D180): the merged roster CSV → a restore snapshot (pure, writes nothing to any cloud) and the headshot corpus → the image bucket through `encodeHeadshot`. The snapshot is then written by `restore`. Procedure in `docs/initial-build/CUTOVER-PLAN.md` §5.
- `npm run backfill:full-name --workspace apps/api` — one-off in-place data fix (D181): sets `fullLegalName` to the first/middle/last join wherever it is blank, never touching a filled value or any other field. `--dry-run` / `--confirm <project-id>`; ⚠ force a cold start right after a real run, or the change is invisible and edits to those records 412 until then.
- `npm run headshots:bulk --workspace apps/api` — load a batch of prepared headshots onto a live directory (D182): objects first, pointer last, a brother's own photo never overwritten; `--plan` / `--undo` / `--purge`, `--dry-run` / `--confirm <project-id>`. ⚠ Needs a cold start right after; run it in maintenance (`infra/maintenance-begin.sh`/`-end.sh`, safe on production since D187) or with `--book-up`. The procedure is in `infra/RUNBOOK.md`.
- `npm run ghost:seed --workspace apps/api` — the **Ghost pull-and-seed** (D183): links each profile to its Ghost member (`ghostMemberId`), carries the Ghost note into a blank `adminNote`, and overwrites the genesis placeholder newsletter consent from Ghost. `--plan` writes a reviewable plan file and changes nothing; `--apply <plan> --confirm <project-id>` carries out exactly that file. ⚠ It **writes to Ghost too** (moves an alternate-address member to the Book primary) and never deletes a member. ⚠ The plan and run files hold real member emails (`restore-artifacts/`, gitignored). ⚠ Cold start right after an apply. Procedure in `infra/RUNBOOK.md`.
- **Production** (`pbe-book-prod`) deploys **only** via `Deploy production` (`deploy-prod.yml`), a manual dispatch on a `v*` release tag that re-runs the full gate first; it has no seeding steps and never will. **A release happens only on Forrest's explicit go-ahead, and he approves the deployment himself** in the `production` GitHub Environment — Claude prepares, tags and dispatches, and never approves (D184). Always released from `main`, so keep `main` releasable. Procedure: `infra/RUNBOOK.md`, "Releasing to production". `infra/environments/prod.env` is its source of truth; the infra scripts take `ENV_FILE=infra/environments/prod.env`.
- CI runs the same gate on every **pull request**, and that run is the authoritative one (D143). Merging to `main` auto-deploys staging (`pbe-book-staging.web.app`): the deploy workflow triggers on the push to `main` itself, trusting the PR gate that already passed on that tree. There is deliberately **no post-merge CI re-run** — it would replay a known-green result against an identical tree.

The log is huge: **consult the index first and read only the governing entries — never read the whole log.** `docs/initial-build/history/` is frozen history — never edit it. DATABASE-SCHEMA §3 is authoritative for field names and semantics.

Deferred work and bugs are Linear tickets (team Techgnosys, project PBE-Book, `OFC-*`): file tickets for anything deferred, close them with evidence when resolved.

## Standing invariants (landmines — do not violate)

- **This repo is PUBLIC.** No secrets and no real member PII anywhere in the tree — ever. Fake-data exemplar is "James Smyth '84 (#5247)"; fake Constitution IDs are > #5000.
- **A real brother's name is never written to this repo — not in the tree, not in a commit message, not in a PR description** (N158, Forrest's call). Write **"the reporter"**, "a UAT tester", "a brother". Forrest's own name is the exception. **Names in Linear are correct and wanted** — the tracker is private and knowing who to talk to is the point; the public/private boundary falls between the ticket and the commit. ⚠ The leak path is the in-app bug reporter, which stamps `Bug report from ⟨name⟩ (#9006)` into every UAT ticket: a session reads it as ordinary context and carries the name into the prose it writes. Redact **on the way out**, in the doc, the commit message and the PR body. No gate can catch this — a check would have to list real brothers' names to find them.
- **WCAG 2.2 AA is a CI-gated hard requirement** (D79), including keyboard alternatives for every drag interaction (2.5.7).
- PII JSON endpoints (`/api/profiles`, `/api/me`, `/api/profiles/{id}`) are `Cache-Control: no-store` (D95). Member images are app-served from the private bucket via `/img/*` behind the session cookie; there is **no CDN and no external load balancer** (D126).
- Server-side per-role projection (`apps/api/src/projection/`) is the **single visibility-enforcement point** (D5/D82). Unlisted (D124) and de-brothered (D115) records are whole-record-omitted from the brother view.
- Cloud Run runs `max-instances=1` + scale-to-zero — one authoritative in-memory instance by design, not autoscaling (D83).
- The session cookie **must be named `__session`** — Firebase Hosting strips every other request cookie before Cloud Run (N5).
- The Firebase CLI deploy step is **pinned to Node 20** (google-auth-library STS dies under newer Node) — don't remove the pin (see `infra/README.md`).
- `DevIdentityProvider` stays compiled out of the prod bundle (D108); the gate's `assert:no-dev-provider` enforces it.
- **No Mixpanel session replay or autocapture in the SPA** (D138/D140); the gate's `assert:no-session-replay` enforces it. Replay captures the rendered DOM, so one recording of a Directory page would ship other brothers' PII around the D5/D82 projection. The newsletter theme deliberately runs the *opposite* configuration — don't "harmonize" them.
- **Analytics events carry no URL.** Mixpanel attaches `$current_url` (and referrer properties) to every event by itself, and on this site a URL names a brother (`/brother/5247`) or carries the search box (`?q=`). `BLOCKED_PROPERTIES` in `apps/web/src/lib/analyticsConfig.ts` strips them; keeping event payloads P6-clean depends on the app code **and** that config together (N125).
- Ghost integration is tested against self-hosted **ghost-staging** (`staging.pbe400.org`), never the live pbe400.org until production cutover. The Ghost auth-bridge theme files have a byte-identical mirror in `ghost-bridge/` — keep it in sync with the `pbe-news-ghost-theme` repo.
- Staging's data reseed is **switched by the repo variable `STAGING_AUTOSEED`**, so check it (`gh variable list`) before assuming either behaviour. **Currently `true`** — re-enabled 2026-10-04 after D132's UAT freeze (`false` from 2026-08-11) — so every deploy **wipe-reseeds `profiles` *and* `users` (per-viewer stars)** (N18, N90/OFC-197): hand edits don't survive, and the tester link is re-applied automatically. Unset behaves the same; only `false` skips the reseed, and then a deploy ships code but **leaves staging data and stars as they are**. Gate 4's migration pause (D189) is on only while it is `false`. (Column preferences live in browser localStorage and are *not* reset by a deploy — clear them in-app via the column picker's "Reset to default columns", or clear site data.)
- Book is the membership system-of-record: a brother may legitimately have **no email and no Ghost account** (~1/3 of records). Every Ghost operation must tolerate Ghost-less brothers.
